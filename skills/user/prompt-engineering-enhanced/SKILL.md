# Prompt Engineering Skill (Claude Code Enhanced)

## Trigger
Use this skill when:
- Crafting prompts for Claude Code or any AI system
- Getting poor quality responses
- Need to communicate complex requirements
- Planning architecture or implementation
- User asks for help with prompting

## 核心真理

**来自资深工程师**:
> "人们花数周学习框架和工具，
> 但零时间学习如何与生成代码的东西沟通"

**基本事实**:
```
提示 = 沟通
清晰 > 模糊，每次都是

糟糕输入 = 糟糕输出
好输入 = 好输出
没有捷径
```

## 黄金法则

### 法则 1: 具体 > 模糊

**对比**:

❌ **模糊（会得到垃圾）**:
```
"给我构建一个认证系统"
"优化这个代码"
"修复这个 bug"
"让网站更快"
```

✅ **具体（会得到你想要的）**:
```
"使用现有 User 模型构建邮箱/密码认证，
会话存储在 Redis 中，24小时过期，
添加中间件保护 /api/protected/ 下的所有路由"

"重构 getUserData 函数使用缓存，
减少数据库查询，保持相同的 API 接口"

"修复 /api/login 在空密码时返回 500 而非 400 的问题"

"优化首页加载:
- 图片懒加载
- 代码分割
- 目标 LCP < 2.5s"
```

**为什么**:
```
模糊 = AI 自由发挥 = 可能过度工程化/错误方向
具体 = 明确约束 = 精准输出
```

---

### 法则 2: 约束 > 开放式

**提供约束**:

#### 技术约束
```
"使用 TypeScript strict mode"
"保持与现有 API v2 兼容"
"不要添加新依赖"
"必须在 Node.js 18+ 运行"
```

#### 架构约束
```
"遵循现有的 Repository 模式"
"使用已有的 ErrorHandler 中间件"
"不要修改数据库 schema"
```

#### 性能约束
```
"这个函数每秒调用 1000 次，必须 < 10ms"
"总 bundle 大小不能超过 500KB"
"API 响应时间 < 200ms"
```

#### 范围约束
```
"只修改 auth.ts，不要碰其他文件"
"这是临时修复，不要重构整个模块"
"保持简单，一个文件搞定"
```

---

### 法则 3: 示例 > 描述

**展示而非告诉**:

❌ **只描述**:
```
"创建一个 REST API endpoint 处理用户登录"
```

✅ **给示例**:
```
"创建登录 endpoint，像这样:

POST /api/auth/login
Request: { email: string, password: string }
Response: { token: string, user: { id, email, name } }

错误处理:
- 400: 缺少字段
- 401: 凭证无效
- 429: 速率限制

现在实现完整的 endpoint"
```

**为什么有效**:
```
Claude 超级擅长:
- 识别模式
- 遵循示例
- 理解具体的成功标准
```

---

### 法则 4: 说"为什么"

**不只是"做什么"，还要"为什么"**:

❌ **只说做什么**:
```
"使用 TypeScript strict mode"
"添加错误处理"
"实现缓存"
```

✅ **说明为什么**:
```
"使用 TypeScript strict mode，
因为我们在生产环境遇到过 implicit any 类型的 bug"

"添加错误处理，
因为这个 API 会被移动客户端调用，
网络不稳定时需要优雅降级"

"实现 Redis 缓存，
因为这个查询每秒被调用 500 次，
数据库 CPU 已经到 80%"
```

**为什么有效**:
```
给出原因 → Claude 理解上下文
→ 做出更好的判断
→ 处理你没预料到的边缘情况
```

## Claude Code 特定技巧

### 技巧 1: 告诉它不要做什么

**Claude 4.5 的倾向**:
- 喜欢过度工程化
- 创建额外的文件
- 添加不必要的抽象
- 提供你没要求的灵活性

**对策**:
```
"保持简单。
不要添加我没要求的抽象。
不要创建额外的文件。
如果可能，一个文件搞定。"
```

**示例**:

❌ **没有约束**:
```
"创建一个配置管理器"

Claude 可能创建:
- ConfigManager.ts
- ConfigValidator.ts
- ConfigLoader.ts
- IConfig.ts
- ConfigError.ts
- index.ts
```

✅ **有约束**:
```
"创建一个简单的配置管理器。
一个文件。
不要过度抽象。
只需要 get/set 功能。"

Claude 创建:
- config.ts（一个文件，简单直接）
```

---

### 技巧 2: 架构优先

**永远在实现前就架构达成一致**:

**正确流程**:
```
1. 使用 Plan Mode（Shift+Tab 两次）
2. 描述想要什么
3. Claude 提出架构方案
4. 你审查并调整
5. 达成一致后
6. 切换到 Sonnet 实现
```

**示例对话**:

```
You: [在 Plan Mode]
"我需要添加用户认证。
我们已经有 User 模型在 Prisma。
建议一个架构。"

Claude:
"基于你的需求，建议:
1. 认证中间件（middleware/auth.ts）
2. 认证路由（routes/auth.ts）
3. 认证服务（services/auth.ts）
4. 会话管理（使用 Redis）

这样分离关注点..."

You:
"不需要独立的服务层。
直接在路由处理器中处理逻辑。
同意其他部分。"

Claude:
"明白。修改后的架构:
1. 中间件（middleware/auth.ts）
2. 路由 + 逻辑（routes/auth.ts）
3. Redis 会话管理

现在实现？"

You:
"是的，开始实现"
[退出 Plan Mode，Claude 开始编码]
```

---

### 技巧 3: 分阶段请求

**复杂任务分步骤**:

❌ **一次要求所有**:
```
"构建完整的用户管理系统，
包括认证、权限、个人资料编辑、
邮件验证、密码重置、
2FA、审计日志"
```

✅ **分阶段**:
```
阶段 1:
"首先，实现基本认证:
- 登录
- 登出
- 会话管理
不要其他功能，先把这个做对"

阶段 2:
"现在添加密码重置:
- 重置令牌生成
- 邮件发送
- 令牌验证
- 密码更新"

阶段 3:
"添加权限系统..."
```

**为什么**:
```
每阶段独立、清晰
更容易审查
问题早发现
可以调整方向
```

## 提示模板

### 模板 1: 功能实现

```
实现 [功能名称]

要求:
- 使用 [技术栈]
- 遵循 [架构模式]
- 保持与 [现有系统] 兼容

约束:
- [性能约束]
- [技术约束]
- [范围约束]

示例:
[提供输入/输出示例]

不要:
- [明确不要做的事]

原因:
[说明为什么需要这个功能]
```

### 模板 2: 代码重构

```
重构 [文件/函数名]

目标:
- [主要改进点]

保持:
- [必须保持不变的]
- [现有 API 兼容性]

改进:
- [性能]
- [可读性]
- [可维护性]

不要:
- 改变现有行为
- 添加新功能
- [其他禁止项]

测试:
[如何验证重构成功]
```

### 模板 3: Bug 修复

```
修复 [Bug 描述]

重现步骤:
1. [步骤 1]
2. [步骤 2]
3. [步骤 3]

预期行为:
[应该发生什么]

实际行为:
[实际发生什么]

已知信息:
- [错误消息]
- [日志]
- [尝试过的调试步骤]

可能原因:
[你的猜测]

约束:
- 最小化改动
- 不要重构无关代码
```

### 模板 4: 架构规划

```
[在 Plan Mode 中使用]

规划 [功能/系统名称]

需求:
1. [需求 1]
2. [需求 2]
3. [需求 3]

现有系统:
- [相关的现有组件]
- [需要集成的部分]

约束:
- [技术约束]
- [性能要求]
- [兼容性要求]

请提出:
1. 推荐的架构
2. 文件/模块结构
3. 主要的权衡考量
4. 潜在的风险

不要立即实现，只是规划
```

## 常见场景

### 场景 1: 从头构建功能

**步骤**:
```
1. Plan Mode: 描述需求
2. Claude 提出架构
3. 你审查并调整
4. 达成一致
5. 实现第一部分
6. 审查并测试
7. 实现下一部分
8. 重复
```

**提示示例**:
```
[Plan Mode]
"我需要构建博客评论系统。

需求:
- 用户可以评论文章
- 支持回复评论（一级嵌套）
- 实时更新（WebSocket）
- 审核功能（管理员）

现有技术栈:
- Next.js 14
- Prisma + PostgreSQL
- NextAuth 用于认证

请提出架构方案"
```

### 场景 2: 调试问题

**步骤**:
```
1. 收集信息:
   - 错误消息
   - 日志
   - 重现步骤
   
2. 提供完整上下文给 Claude

3. Claude 分析并建议

4. 尝试修复

5. 如果不工作，提供新信息

6. 迭代直到解决
```

**提示示例**:
```
"调试登录失败问题

症状:
用户点击登录后，页面无限加载

错误:
控制台显示: 'TypeError: Cannot read property 'token' of undefined'

代码:
[粘贴相关代码]

已尝试:
- 检查 API 返回 → 正常
- 检查网络请求 → 200 OK
- 控制台无其他错误

环境:
- Chrome 120
- 只在生产环境发生
- 开发环境正常

分析可能原因并建议修复"
```

### 场景 3: 性能优化

**步骤**:
```
1. 识别性能问题
2. 提供性能数据
3. 设定目标
4. Claude 建议优化
5. 实现并测试
6. 测量改进
```

**提示示例**:
```
"优化首页加载性能

当前指标:
- LCP: 4.2s（目标 < 2.5s）
- FID: 180ms（目标 < 100ms）
- CLS: 0.15（目标 < 0.1）

Lighthouse 报告显示:
- 最大的问题: 大图片（5MB hero image）
- JavaScript bundle: 800KB
- 未使用的 CSS: 300KB

建议具体的优化步骤，
优先处理最大的性能问题"
```

## 避免的错误

### 错误 1: 假设 Claude 知道你的上下文

❌ **错误**:
```
"修复那个 bug"
"优化性能"
"添加那个功能"
```

✅ **正确**:
```
"修复登录页面的 CORS 错误"
"优化 /api/users 端点的查询性能"
"添加我们昨天讨论的邮件通知功能"
```

### 错误 2: 过于模糊

❌ **错误**:
```
"让代码更好"
"改进架构"
"修复问题"
```

✅ **正确**:
```
"重构 getUserData 使用缓存减少数据库负载"
"将认证逻辑从路由移到中间件"
"修复空输入时的 500 错误"
```

### 错误 3: 不提供约束

❌ **错误**:
```
"创建一个配置系统"
```

Claude 可能:
- 过度工程化
- 创建 10 个文件
- 添加你不需要的功能

✅ **正确**:
```
"创建简单的配置系统:
- 一个文件
- JSON 格式
- get/set/has 方法
- 不要添加验证、类型系统或其他复杂功能"
```

### 错误 4: 忘记说为什么

❌ **错误**:
```
"添加缓存"
```

✅ **正确**:
```
"添加 Redis 缓存，
因为这个查询每秒被调用 500 次，
数据库 CPU 已经到 80%，
数据可以安全缓存 5 分钟"
```

### 错误 5: 一次要求太多

❌ **错误**:
```
"构建完整的电商系统，
包括产品、购物车、支付、
订单管理、库存、配送、
用户评论、推荐系统、
管理后台、分析仪表板"
```

✅ **正确**:
```
"先实现核心产品展示:
- 产品列表
- 产品详情
- 基础搜索

其他功能稍后添加"
```

## 高级技巧

### 技巧 1: 使用 CLAUDE.md 提供项目上下文

**在 CLAUDE.md 中**:
```markdown
# 项目: 电商平台

## 技术栈
- Next.js 14 (App Router)
- Prisma + PostgreSQL
- Stripe 支付
- NextAuth 认证

## 架构模式
- Repository 模式（所有数据库访问）
- 服务层（业务逻辑）
- API 路由（HTTP 处理）

## 代码规范
- 使用 TypeScript strict mode
- 所有 async 函数必须有错误处理
- API 响应格式: { success, data?, error? }

## 性能要求
- API 响应 < 200ms
- 首页 LCP < 2.5s
- 所有图片使用 Next/Image

## 不要
- 不要使用 class components
- 不要添加未在 package.json 的依赖
- 不要修改 Prisma schema 不先讨论
```

**结果**: 每次提示都自动有这个上下文

### 技巧 2: 提供成功标准

```
"实现用户搜索功能

成功标准:
1. 输入 'john' 返回所有名字包含 john 的用户
2. 搜索不区分大小写
3. 返回最多 20 个结果
4. 响应时间 < 100ms
5. 空查询返回空数组，不报错

测试:
curl -X POST /api/search -d '{"query": "john"}'
应该返回匹配的用户列表"
```

### 技巧 3: 学习和复制好的模式

**如果 Claude 生成了好代码**:
```
"这个实现很好。
使用相同的模式实现 [其他功能]"
```

**示例**:
```
"你刚写的 createUser 函数很好:
- 清晰的错误处理
- 类型安全
- 适当的日志

使用相同的模式实现 updateUser 和 deleteUser"
```
