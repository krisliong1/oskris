# Context Window Monitor Skill

## 🚨 核心发现（研究支撑）

Context Window 性能降级不是在 100% 时才发生！

### 研究来源：
1. **Chroma Research (2025)** - "Context Rot" 报告，测试了 18 个 LLM
   - 发现：性能随 input 长度增加而**持续降级**
   - 不是线性降级，而是有突然的"悬崖式"下降点
   - 来源：https://research.trychroma.com/context-rot

2. **arXiv 论文 (2025-12)** - "Context Discipline and Performance Correlation"
   - 发现：KV cache 增长导致**非线性性能降级**
   - 来源：https://arxiv.org/abs/2601.11564

3. **arXiv 论文 (2025-09)** - "Maximum Effective Context Window"
   - 发现：大多数模型在 **1000 tokens** 就开始准确率下降
   - 实际有效窗口 vs 理论最大窗口差距可达 **99%**
   - 来源：https://arxiv.org/abs/2509.21361

4. **Claude Code Ultimate Guide** - Context Window Management
   - 200K token 窗口中，实际可用约 140-150K
   - 系统在 75-92% 时自动触发 compaction
   - **建议在 70% 时就主动 compact**

5. **Factory.ai** - The Context Window Problem
   - "models do not use their context uniformly"
   - 性能随 context 增长变得越来越不可靠

### 降级阶段（基于研究总结）：

```
0-20%   ✅ 最佳性能区 - 完全正常
20-40%  ⚠️ 早期降级 - 开始出现细微质量下降
40-60%  🟡 明显降级 - 回复变短、推理变浅、容易遗漏细节
60-80%  🔴 严重降级 - 经常忘记上下文、重复内容、推理错误增多
80-100% ❌ 危险区 - 基本不可靠，必须立即处理
```

## 📊 Claude 在 claude.ai 中的自我监控方法

### 1. 对话轮次估算法
Claude.ai 界面中没有精确的 token 计数器，但可以通过以下方式估算：

```
每轮对话平均消耗：
- 简单问答：500-1,500 tokens
- 代码生成/分析：2,000-8,000 tokens  
- 文件操作（使用工具）：3,000-15,000 tokens
- 长文档分析：5,000-20,000 tokens

估算公式：
预估使用量 = Σ(每轮估计消耗)
预估百分比 = 预估使用量 / 200,000 × 100%
```

### 2. 降级症状自检

Claude 应该在每次回复前自检以下症状：

```
早期症状（20-40%）：
□ 回复开始变短
□ 容易遗漏用户的某些要求
□ 不再主动引用之前对话的细节

中期症状（40-60%）：
□ 开始重复之前说过的内容  
□ 推理步骤减少
□ 忘记用户偏好或配置

晚期症状（60-80%）：
□ 回复明显变笨
□ 工具使用出错增多
□ 不能维持复杂的多步骤任务
□ 开始出现幻觉

危险症状（80%+）：
□ 完全忘记之前的上下文
□ 给出矛盾的回复
□ 工具调用反复失败
```

## 🔄 主动提醒机制

### Claude 必须在以下时间点主动提醒用户：

**每 10 轮对话：**
```
"📊 Context 估计：约 XX% 已使用（第 N 轮对话）
当前状态：[✅正常 / ⚠️注意 / 🔴危险]
建议：[继续 / 考虑开新对话 / 立即开新对话]"
```

**检测到降级症状时：**
```
"⚠️ 我注意到当前对话较长，context 可能已经达到 ~XX%。
研究表明这个阶段性能会开始降级。
建议：开一个新对话继续，我会把关键信息带过去。"
```

**任务复杂度高时（代码生成、多步骤操作）：**
```
"💡 这个任务比较复杂，为了确保最佳质量，
建议在新对话中执行。当前 context 估计已使用约 XX%。"
```

## 🛡️ 缓解策略

### 在 Claude.ai 中：
1. **主动建议开新对话** - 最有效的"重置"方法
2. **精简回复** - 减少不必要的解释和格式
3. **分批处理** - 复杂任务拆分到多个对话
4. **总结关键信息** - 在提醒时列出需要带到新对话的信息

### 在 Claude Code 中：
1. `/compact` - 在 70% 时主动执行
2. `/clear` - 完全重置（需先保存状态）
3. `/status` - 检查当前 context 使用量
4. 复制粘贴重置法：复制 → `/compact` → `/clear` → 粘贴

## 📋 轮次-百分比快速参考

```
对话轮次    预估 Context    状态        建议
──────────────────────────────────────────
1-5轮      ~5-15%         ✅ 最佳     放心使用
5-10轮     ~15-30%        ✅ 良好     正常使用
10-15轮    ~30-45%        ⚠️ 注意     考虑效率
15-20轮    ~45-60%        🟡 降级     开始精简
20-30轮    ~60-80%        🔴 危险     强烈建议开新对话
30+轮      ~80%+          ❌ 严重     必须开新对话

注意：以上是估算值，实际取决于每轮的复杂度。
使用工具（bash、浏览器等）会消耗更多 token。
```

## 🎯 与其他 Skill 的集成

这个 Skill 应与所有其他 Skill 配合使用：
- **core-work-rules**: 在 context 高时，默认使用最小修改模式
- **work-rules**: 优先级：context 管理 > 完美输出
- **project-workflow**: 复杂项目自动拆分到多个对话
- **所有 Skills**: 在 context > 50% 时提醒用户

## 📝 记住

```
❌ 错误认知：Context Window 到 100% 才会有问题
✅ 正确认知：20-40% 就开始降级，是渐进式的

❌ 错误做法：一直在同一个对话中工作到极限
✅ 正确做法：主动监控，提前预防，适时开新对话

❌ 错误做法：等用户发现质量下降才处理
✅ 正确做法：主动提醒用户，在降级前就采取行动
```
