## 🎯 核心原则（从文章提炼）

### 1. 先思考，再输入 (Think First)

**关键洞察**:
> "10/10 次，使用 Plan Mode 的输出远胜于直接开始输入"

**为什么重要**:
- 大多数人以为 AI 工具就是"开始说话"
- **这是最大的错误**
- 真正的流程：**思考 → 计划 → 执行**

**两种建议路径**:

#### 路径 A: 有经验的开发者
- 直接思考架构
- 规划系统设计
- 考虑权衡取舍

#### 路径 B: 新手开发者
1. 与 ChatGPT/Gemini/Claude 深度对话
2. 描述你想构建什么
3. 询问 LLM 各种系统设计选项
4. **双向提问**（不是单向）
5. 最终共同确定解决方案

**适用场景**:
- ✅ 构建功能前 → 思考架构
- ✅ 重构代码前 → 思考最终状态
- ✅ 调试前 → 思考已知信息
- ✅ 总结邮件前 → 思考关键点

**模式规律**:
```
思考优先 + 后输入 = 卓越结果
直接输入 + 希望 Claude 搞定 = 糟糕结果
```

### 2. 架构比一切都重要

**作者警告**:
> "架构就像只给出输出，没有过程。这留下了巨大的空间让 AI 自由发挥，这就是 AI 生成代码的问题所在"

**对比示例**:

❌ **模糊请求**:
```
"给我构建一个认证系统"
```

✅ **专业请求**:
```
"使用现有 User 模型构建邮箱/密码认证，
会话存储在 Redis 中，24小时过期，
添加中间件保护 /api/protected 下的所有路由"
```

**差距分析**:
- 模糊请求 = AI 自由发挥 = 可能过度工程化
- 具体请求 = 明确约束 = 精准输出

**如何使用 Plan Mode**:
```
Shift + Tab (两次) = 进入 Plan Mode
花费 5 分钟规划 = 节省数小时调试时间
```

### 3. CLAUDE.md - 你的杠杆点

**CLAUDE.md 是什么**:
- Markdown 格式文件
- AI 模型处理 Markdown 极其高效
- Claude 每次会话第一件事：读取 CLAUDE.md
- **就像每次对话前的入职培训**

**大多数人的错误**:
1. 完全忽略它
2. 塞满垃圾信息 → 让 Claude 变更差

**正确使用方法**:

#### 规则 1: 保持简短
- Claude 每次只能可靠遵循 **150-200条指令**
- Claude Code 系统提示已占用 **~50条**
- 你的 CLAUDE.md 不能太长
- **如果太长 = Claude 会随机忽略某些东西**

#### 规则 2: 项目特定
- ❌ 不要解释什么是 components 文件夹
- ✅ 告诉它奇怪的东西（项目特有的 bash 命令）
- ✅ 工作流中的所有内容都应该写进去

#### 规则 3: 告诉它"为什么"，不仅是"什么"
❌ "使用 TypeScript strict mode"
✅ "使用 TypeScript strict mode，因为我们在生产环境遇到过 implicit any 类型的 bug"

**为什么有效**:
- Claude 像人类一样
- 给出原因 → Claude 实现更好
- 为什么提供了判断的上下文

#### 规则 4: 持续更新
- 按 `#` 键 → Claude 自动添加指令到 CLAUDE.md
- 发现自己纠正 Claude 同样的事情两次 → 应该写进文件
- **CLAUDE.md 是活文档**，记录代码库如何工作

**对比**:
```
❌ 糟糕的 CLAUDE.md = 给新员工的文档
✅ 优秀的 CLAUDE.md = 假设明天失忆给自己的笔记
```

### 4. 上下文窗口的限制

**令人震惊的真相**:
- Opus 4.5 有 **200,000 token** 上下文窗口
- ⚠️ **但质量在 20-40% 时就开始下降**！
- 不是在 100% 时才降级

**实际情况**:
```
20-40% 使用 = 开始降级
100% 使用 = 已经很糟糕了
```

**为什么 Compacting 不能救你**:
- 如果已经降级了，Compacting 也无法恢复质量
- Compacting 不是魔法

**累积的东西**:
- 每条消息
- 每个读取的文件
- 每段生成的代码
- 每个工具结果

### 5. 实用管理技巧

#### 技巧 1: 作用域对话
```
一个对话 = 一个功能/任务
```

❌ **错误**: 同一对话构建认证系统 + 重构数据库层  
✅ **正确**: 分开两个对话

**为什么**: 上下文会混在一起，Claude 会困惑

#### 技巧 2: 使用外部记忆
创建文件存储计划和进度:
- `SCRATCHPAD.md`
- `plan.md`

**好处**:
- 跨会话持久化
- 明天回来 → 读取文件 → 继续工作
- 不是从零开始

**高级技巧**:
- 把这些文件放在**层级结构顶部**
- 这样每个任务/功能都能使用

#### 技巧 3: 复制粘贴重置法
**强大的重启技巧**:

```bash
1. 复制终端所有重要内容
2. 运行 /compact 获取总结
3. 运行 /clear 完全清空上下文
4. 粘贴回重要信息
```

**结果**: 全新上下文 + 保留关键信息

#### 技巧 4: 知道何时清空
- 对话跑偏了？
- 累积了无关上下文？
- **直接 /clear 重新开始**

**重要**:
- Claude 仍有你的 CLAUDE.md
- 不会丢失项目上下文
- **9/10 次，用 clear 更好**（反直觉但真实）

```
人们花数周学习框架和工具

```

- 是最基础的沟通形式
- 清晰 > 模糊，每次都是

### 7. 有效提示的方法

#### 方法 1: 具体说明想要什么
❌ "构建认证系统" → Claude 自由发挥（会用得很差）

✅ "使用现有 User 模型构建邮箱/密码认证，会话存储在 Redis，添加中间件保护 /api/protected 路由"

**即使这样也不完美，但已经清晰得多**

#### 方法 2: 告诉它不要做什么
**Claude 的倾向**:
- Claude 4.5 特别喜欢**过度工程化**
- 额外的文件
- 不必要的抽象
- 你没要求的灵活性

**解决方案**:
```
"保持简单。不要添加我没要求的抽象。
如果可能，用一个文件搞定。"
```

**重要提醒**:
- 始终交叉检查 Claude 生成的内容
- 不要盲目信任
- AI 是加速我们，不是完全替代我们
- Claude 仍会犯错

#### 方法 3: 给出原因
```
"这需要快，因为每个请求都要运行它"
→ 改变 Claude 处理问题的方式

"这是个原型，我们会扔掉它"
→ 改变什么权衡是合理的
```

**Claude 无法读心**: 你没提到的约束，它不知道

### 10. 模型差异

**Sonnet vs Opus**:

#### Sonnet (更快更便宜)
- ✅ 执行任务，路径清晰时
- ✅ 写样板代码
- ✅ 基于特定计划重构
- ✅ 实现已做出架构决策的功能

#### Opus (更慢更贵)
- ✅ 复杂推理
- ✅ 规划
- ✅ 需要深度思考权衡的任务

**推荐工作流**:
```
1. 使用 Opus 规划和架构决策
2. 切换到 Sonnet (Shift+Tab) 实现
```

**如何切换**:
- 在 Claude Code 中按 Shift+Tab
- CLAUDE.md 确保两个模型在相同约束下运行
- 交接流畅

**开玩笑**:
> "如果通过 API 使用，考虑卖肾吧"

### 12. MCP (Model Context Protocol)

**MCP 是什么**:
- 让 Claude 连接外部服务
- Slack, GitHub, 数据库, APIs

**何时使用**:
- 发现自己不断从某处复制信息到 Claude
- → 可能有 MCP server 能自动完成

**MCP 市场**:
- 有很多 MCP 市场
- 如果不存在 = 自己创建（就是获取结构化数据的方式）
- 作者说他会很惊讶找不到

---

### 13. Hooks

**Hooks 是什么**:
- Claude 修改前/后自动运行代码

**示例**:
- 想要 Prettier 在每个 Claude 接触的文件上运行？ → Hook
- 想要每次编辑后类型检查？ → Hook

**好处**:
- 立即捕获问题
- 不让它们堆积

**额外好处**:
- 帮助移除技术债务
- 设置特定 hook，每 1000 行后清理代码
- Claude 审查 PR 时很有用

---

### 14. 自定义 Slash 命令

**是什么**:
- 重复使用的提示，打包成命令
- 创建 `.claude/commands` 文件夹
- 添加 markdown 文件（你的提示）
- 用 `/commandname` 运行

**何时使用**:
- 经常运行相同类型任务
- 调试、审查、部署 → 做成命令

### 17. 解锁技巧

#### 技巧 1: 清空对话
```bash
/clear
```
- 累积的上下文可能在困扰它
- 给一个全新开始

#### 技巧 2: 简化任务
- Claude 在复杂任务上挣扎？
- → 分解成更小的块
- 每块工作后再组合

**注意**:
> "但实际上，如果 Claude 在复杂任务上挣扎，
> 说明你的 plan mode 不够充分"

#### 技巧 3: 展示而非告诉
- Claude 不断误解？
- → 自己写个最小示例
- "这是输出应该看起来的样子。现在对其余部分应用这个模式"

**Claude 超级擅长**:
- 理解成功标准长什么样
- 遵循好的示例

#### 技巧 4: 有创意
- 有时你框架问题的方式对 Claude 不适用
- 重新框架：
  - "把这实现为状态机" vs "处理这些转换"
  - 可以解锁进展

